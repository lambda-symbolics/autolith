# 0.67.36

## Channels and the shared world

Autolith now runs ordinary sessions as channels in one background world server, rather than starting an agent process for every terminal. Each channel has an identifier, working directory and durable conversation history. You can keep several channels open, work in different repositories, visit a child agent and return to your original conversation.

Run `autolith` in a directory to connect to the server, starting it when needed. Autolith opens that workspace's most recently active channel that another terminal is not controlling, or creates one. Use `autolith open ID` for a specific channel. Inside Autolith, use `(switch)` for the picker or `(switch "ID")` to select a channel. An unambiguous identifier fragment is enough.

Closing a terminal or disconnecting leaves its channel running. Use `(detach)` or press Ctrl-Z to detach deliberately, and use `(quit)` to end the channel. Inspect the shared server with `autolith lg status`; stop all its channels and the server with `autolith lg stop`. Shutdown now waits for confirmed server exit. A failed server startup reports its cause instead of silently running a separate agent in the terminal process.

Channels that have no attached terminal, running work or pending work unload after the configured idle interval, 30 minutes by default. Opening one or delivering a message to its agent serves it again from its durable history.

### A channel, an agent and a terminal are different things

A channel is a conversation and execution location. A participant is a person or an agent with an identity and private state. An agent resides in at most one channel, and a channel has at most one resident agent. A terminal shows or controls a channel; switching its view moves nobody.

You are the human participant, initially named `user`, and reside in your own `inbox`. No agent resides there. Agents start with workspace-derived names such as `frob` and `frob-2`; children use the names their parents supplied. Handles are unique and case-insensitive. Use `(rename "reviewer")` to rename the current channel's agent, or `(rename "WHO" "NAME")` to rename a particular participant, including yourself.

Durable conversations and channels share their identifiers and history. Read `channel:id/ID` to inspect a channel, `channel:current` for the current channel and its children, or `channel:list` to discover others. Existing conversation histories migrate onto the corresponding channels and participants without creating new identities each time they are opened.

## Messages, mentions and the human inbox

Use `(tell "ID" "Please review the change")` to send a message as yourself. The destination can be a channel identifier fragment or a handle such as `@reviewer`. Use `(tell)` to choose a channel and prepare the form for your message.

You can also mention someone directly in a submitted prompt: `@reviewer please check the failure path`. Mention completion is available in the composer. Mentions go to the participant's current channel before your local agent takes the prompt. An `@` inside an email address or path does not count as a mention.

Agents use `channel.send`, `channel.subscribe` and `channel.unsubscribe`. Messages reach the destination's residents, its subscribers and mentioned participants. An idle agent receives a new turn; a busy agent receives a steer labelled with the sender and source channel. Subscribers also receive copies of ordinary typed messages and agent replies from channels they follow. Children send as their own participants under their role's tool policy.

`@parent` addresses the sender's parent. If that parent is parked, delivery proceeds to the nearest ancestor agent with a channel, or to you when there is none.

Messages addressed to or mentioning you are notices in your inbox, not prompts for an agent. Open it with `(switch "inbox")`. Notices wait unread until a terminal displays them, then appear in full with a return command for their source channel. Use `(tell "ID" "text")` to reply from the inbox.

Incoming deliveries and outgoing sends are durable. Full inboxes and interrupted delivery are retried using the original message identifier, and replay after a crash does not add a second copy. The sender receives a report of destinations still waiting. Messages for an agentless channel wait until an agent resides there.

## Moving and parking agents

Use `(move "WHO")` to bring an existing agent into the current channel, or `(move "WHO" "ID")` to select its destination. Use `(move)` for pickers, `(dismiss "WHO")` to park an agent without deleting it, and `(domestic)` to create a new agent in an empty channel.

Moving or parking first stops the current turn at a safe boundary: an in-flight tool call finishes, no new provider request starts, and prompts not yet started are dropped with a notice in the old channel. A move into an occupied channel or the human inbox is refused.

The agent takes its model and existing context with it. At the destination, it receives activity from the move onward; the channel's earlier history is available to read but is not automatically inserted into that context. Private context is saved before residence changes and restored before the next turn, including after a restart or a partially completed move.

Goals and missions follow the agent. A running mission arrives paused, with its mission jobs cancelled; use `(mission :resume)` to resume it. Other jobs already started keep running in their original channel and record their results there without waking an agent there. Moving a child that is still executing a parent's assignment cancels that assignment and reports the outcome to the parent. The child's own children continue.

A parked agent has no channel but keeps its identity, context and children. Bring it back with `(move "WHO")`. Parking does not park its children, and mentioning a parked agent reports that it has no delivery destination. A channel left without an agent retains its history and subscribers. Supply an agent with `(move "WHO")` or create one with `(domestic)` before submitting prompts there. A domestic agent starts with no inherited private context and can read the channel's history.

## Durable children and assignment jobs

A child agent now has a durable identity, channel, name, role and conversation history. Finishing an assignment does not delete it. Reuse an idle child by sending another assignment through its channel; `channel:current` shows your children and whether each is busy. An agent can keep up to 32 children, and children may create their own children within the configured depth and role limits.

Visit a child channel to inspect its transcript or work with it directly. Its role's instructions and tool permissions apply there too. Opening its channel does not turn it into an unrestricted top-level agent.

Use the lifecycle operation that matches the work:

- `child.spawn` creates a child and starts its assignment.
- `channel.send` assigns more work to an existing idle child or steers a busy one.
- `job.get`, `job.wait` and `job.cancel` inspect, await or cancel an execution. Cancelling a job does not delete its child agent.
- `child.rename` changes the child's name.
- `child.compact` summarizes an idle child's history; `child.reset` clears it.
- `child.remove` explicitly deletes an idle child, its channel and its descendants. Children are not automatically pruned after completion.

Completion results belong to the conversation that started the work. Nonblocking work detaches by default; completion policy `continue` can wake that owning conversation, while `notify` waits for an ordinary turn.

Channel removal validates the complete selection before changing the world. Storage cleanup has durable retry records, and removed identities cannot reappear from leftover history. Worktree cleanup checks recorded ownership before deletion and preserves unrelated checkouts when ownership cannot be established. Engineering artifacts are independent of checkout cleanup.

## Usage and resource reporting

Conversation-lifetime usage totals survive unloading and reopening, for parent and child channels. Assignment jobs have their own usage and timing. Process-wide spend in `(status)` is labelled as belonging to this process.

Run `autolith usage` to inspect stored data, logical disk usage and process memory across workspaces. Live channels count separately even when they share a server; each process ID counts once, including a world server with no open channels. Disk totals deduplicate file identities across overlapping roots. Memory totals are RSS observations, with unavailable or partial measurements identified explicitly.

## Context accounting and contract recovery

The context meter and automatic compaction reuse measured provider usage across ordinary usage-metadata updates. Previously, those updates could discard the measurement and fall back to a much larger character estimate. Retained reasoning contributes the measured post-response input and output total; new tool evidence and session content are counted separately. The meter distinguishes an exact covered measurement from an estimate with new content. Interrupted response persistence, compaction and context replacement invalidate obsolete measurements.

Contract admission comparison now handles vector-valued arguments structurally across log replay. Replacing an admitted contract can retain its earlier authorization without making the new proposal active. String case and scalar types remain significant, and invalid admission receipts are rejected before appending anything.

Use `(reset-contracts)` or the `contracts.reset` tool to recover even when damaged contract metadata prevents ordinary tool calls. Recovery archives the original log byte-for-byte with private permissions, then atomically removes contracts and saved diagnosis/probe records across all scopes in that store. Facts, evidence, rules, methods, procedures and prose memories are preserved. New contracts can be defined afterward.

On Windows, check workers receive an explicit ColorLisp native-library path resolved before temporary cache isolation, so a mapped DLL does not prevent fixture cleanup.

## Terminal navigation and startup

- The fullscreen sidebar groups channels by workspace and nests children beneath their parents. Your inbox appears first. Working, idle and unloaded channels have distinct markers; attached terminals, unread messages and mentions are shown separately.
- Click a channel to switch to it. Press Ctrl-T to show or hide the sidebar. On narrow terminals, press Ctrl-T for a keyboard drawer, then use the arrow keys and Enter to navigate.
- Human inbox unread counts are durable and shared across terminals. Ordinary channel unread counts are per terminal, while queued-delivery counts identify messages waiting for an unserved channel.
- A loading display appears before opening an inactive channel's host, including when startup takes long enough to notice.
- Prompt recall is initialized when opening and reconnecting channels and reads older input lazily. Cancellation hints use executable Lisp forms with quoted string job identifiers, such as `(job.cancel :id "exec:1")`.
- Retained Markdown is reflowed when the transcript width changes, including sidebar changes. Terminal presentation preferences carry across channel switches and reconnects.
- Interactive onboarding now explains channel navigation, the inbox, agent residence and the separate child and job lifecycles.

## Checkpoints, structured clients and recovery

A checkpoint covers the shared process. New turns wait while active turns and their jobs finish; the server then pauses all channels, saves the image and reconnects attached terminals. Every channel receives the outcome, and the requesting channel receives the generation identifier. On Windows, the launcher restarts the saved exact heap and serves the channels again.

ACP clients use the shared channel runtime as well. Session creation and loading use channel ownership and lifecycle rules, editor disconnection is tolerated during streamed delivery, and synchronous requests wait for channel idle. Caller ASDF settings are restored before executable user initialization while private runtime startup remains isolated. Packaged Nix launchers use a store-resident interpreter when starting the detached world server.

Conversation forks now stream retained history within bounded memory. Transcript queries stream bounded pages, and oversized `resource.read` windows are refused explicitly so callers can request a smaller window. Coordinated startup, deletion and checkpoint admission cover interrupted delivery, concurrent opens and durable cleanup alongside the shared-world lifecycle.
