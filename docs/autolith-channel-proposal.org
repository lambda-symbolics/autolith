* Main change: sessions to a shared world of channels

- Replace the session-centric model with one shared world of channels and participants.
  - Today: each client/server pair centers on a session and its agent.
  - Proposed: one server hosts a cross-project world; multiple clients view and
    interact with its channels and independently identifiable participants.
- Humans and agents use the same participant type, including private context,
  memories, plans, and goals. Their client programs differ.
- A channel is an addressable conversation and execution location. Each participant
  resides in one channel; a channel can have multiple residents.
- Use ordinary channel messages for human/agent, agent/agent, and parent/child work.
  Child agents become directly inspectable participants in the same world.
- Client channel selection is separate from participant residence and subscription.
- Migrate each existing session into a channel plus an agent-operated participant,
  placing history/CWD on the channel and private state on the participant.

* Temporary session migration

- Until the channel/agent model stabilizes, continuously reconcile legacy sessions
  with the channels and participants they map onto, rather than migrating only once.
- If a legacy session is newer than its mapped channel/participant state, migrate it
  again, overwriting that state from the session.
- Preserve the session-to-channel/participant mapping and reuse the same identities
  on repeated migration.
- Remove this reconciliation mechanism once the new model is stable.

- Human and agent clients use the same participant operations. Agent model/role
  settings belong to participant configuration and follow that identity.
- Client views and execution interfaces are implementation-defined, outside the
  shared world schema. Human and agent clients may use different interfaces.
- Store each relationship authoritatively once; derive reverse lookups or maintain
  indexes where needed. The logical records do not require duplicated storage.

* Channels and participants

- Each participant resides in exactly one channel. A channel may have zero or more
  residents, human or agent. Subscription is independent of residence.
- Only the user can move existing participants in the MVP.
  - Move the selected participant into the destination's resident set and remove
    it from the source's. Other residents do not move; there is no automatic swap.
- Participants can discover, inspect, read, subscribe to, and message other channels
  and participants across the world, including across projects.
- Participant parent/child relationships are separate from channel nesting.
- Ownership, residence, and subscription are distinct relationships.
- Preserve human control over the participant tree; detaching/reparenting must not
  leave participants outside that control. Exact descendant controls need specification.

* What belongs where

- Participant: identity, configuration, private context, memories, plans, goals.
  - These belong to humans and agents alike and follow the participant when moved.
  - Context is private working material, subject to compaction, rather than simply
    the history of the currently displayed channel.
  - Plans and goals stay separate.
  - A new participant inherits no private state from previous channel residents.
- Channel: CWD, history, jobs started there.
  - After moving, use the destination's CWD for new work.
  - Record tool calls, tool results, replies, and execution activity in the
    residence channel; messages may explicitly target another channel.
- Workspace: agenda.
  - Use the agenda for the participant's residence workspace, including after a move.
    New residents can read channel history through ordinary reads.
- Top-level agents may self-modify the shared image.

* Communication and resources

- Channels become a resource URI type, as sessions are today.
  - Address channels with channel resource URIs.
  - Read channel state and bounded history through the resource interface.
  - Inspect a child's channel through the same interface as any other channel.
- Messages sent to a channel reach its residents and subscribers through the same delivery path.
- Reading history does not subscribe the reader; subscriptions deliver future messages.
- Mentions deliver across channels without creating a subscription.
- Deliver human and agent messages through the same participant interface.
  - Agent clients trigger inference; human clients present the messages to the user.
  - Working agent recipient: deliver as a clearly labeled steer with sender and source channel.
- Other participants' tool calls, results, and execution activity do not trigger inference.
- Idle agents yield until a message or job completion requires work, without polling.
- Human and agent clients set their own participant presence. Agent clients also expose
  actual working/yielded status and current activity.
- Show sender identities, color-highlight mentions, and expose residents, subscribers,
  channel nesting, participant relationships, presence, and agent execution status.

* Delegation and jobs

- Delegate by creating an ordinary child participant and channel, configuring its
  agent client and model/role, and sending an assignment through channel messages.
- A delegation convenience helper is a procedure over those operations, not
  another helper agent or a separate child communication model.
- Creating a child with its initial residence is distinct from moving an existing participant.
- The parent can read or steer the child without subscribing to all its activity.
- Notify the parent of completion using the same channel-bound job routing.
- Jobs stay in their starting channel when participants move. Jobs cannot be detached
  from that channel.
- Deliver completion to that channel's current residents, including new arrivals;
  wake their agent clients and notify their human clients. An empty channel has no
  resident to wake. Completion does not follow departed participants.
- Moving or deleting a participant does not cancel channel-owned jobs.
- Running jobs block deletion of their channel and state required by the operation,
  not removal of participants merely because they reside there.

* Deletion

- Deleting a participant deletes its owned state: context, plans, goals, and private
  memories, subject to the memory-transfer choice below.
- Residence is not ownership. Before deleting a channel, move its residents or
  explicitly include them in deletion; do not implicitly delete other participants.
- Delete only unreferenced history. Retain referenced history and keep existing
  references resolvable after channel deletion.
- Working choice: move a deleted participant's memories into the global store,
  keeping their unique IDs. They do not become another participant's private memories.
- Recursive deletion must respect ownership and running-job removal checks.

* Server and clients

- One server hosts one authoritative world across projects.
- Extend the existing client-server architecture from 1:1 to N:1.
- Reuse the existing localgroup server lifecycle machinery for shared-world commands.
- The first client starts the server if needed; later clients connect to the same world.
- Each client has an independent interface to shared channels; several clients may
  inspect and interact with the same channel.
- At startup, select the latest-touched channel matching the client's launch CWD,
  or offer to create a new channel there.
- Each channel has its own CWD, independent of the server's launch directory.

* Implementation details left

- Message ordering, batching, deduplication, and self-message handling.
- Atomic residence moves and their boundaries during inference, tool calls,
  and job completion; delivery ordering for multiple residents.
- Ownership, descendant controls, and reference cleanup on deletion.
- Memory transfer, history-reference tracking, and retention of referenced history.
- N:1 startup, reconnection, persistence, concurrent updates, and shared-image mutation.
- CWD matching and the meaning of "latest touched".
- Channel URI addressing, bounded-history schema, and supported resource edits.
- Exact migration fields, freshness comparison, reconciliation triggers, and removal
  of existing 1:1 session assumptions.
