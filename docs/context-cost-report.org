#+TITLE: Autolith Context Cost Report
#+STARTUP: content

Where Autolith spends provider tokens it does not need to spend. Reviewed at
master =ba5ac68= against the two pricing mechanisms that matter: raw prompt
size, and prompt-cache stability (cached input replays at roughly 0.1x list
price on OpenAI and Anthropic, and on subscription routes a cache miss burns
the rate-limit window that =later= exists to ration). Sizes below were
measured in a live image, not estimated from source: the real Autolith workspace
configuration, the full default-plus-task tool registry, tokens approximated
as characters over four.

* The headline numbers

| Fixed request prefix              | chars  | ~tokens |
|-----------------------------------+--------+---------|
| System prompt (Autolith workspace) | 43,252 | 10,800  |
| Tool definitions, 46 tools        | 48,924 | 12,200  |
| Total before any history          | 92,176 | 23,000  |

Every provider request carries roughly 23k tokens before the first message of
history. For comparison, the two OSS inspirations ship a fixed prefix of
about 3-5k tokens: codex sends ~5 tools and a ~2.5k-token prompt, pi sends ~7
tools over a static prompt. Autolith's prefix is 5-8x that, which is
defensible for what Autolith is - but only while the prefix actually caches.
The findings below show it mostly does not.

The cost shape to keep in mind: a 40-turn conversation that has grown to
100k tokens re-sends ~100k input tokens per request. Cached, that costs
~10k-token-equivalents; uncached it costs the full 100k. Every finding here
is either "the prefix is bigger than it needs to be" (paid once per cache
write, and once per miss) or "the prefix changes when it does not need to"
(turns every request into a miss).

* How a request is assembled

The shared Responses builder (=src/provider/wire-protocol.lisp:179=) makes
each request from: an instruction prefix (system prompt, then goal context),
the conversation projection, an instruction suffix (the rendered
request-local context, i.e. contributions from
=src/agent/context.lisp=), and the tool array. Placement is per provider:

- Codex (=:top-level=, =wire-protocol.lisp:165=): prefix AND suffix are
  concatenated into the top-level =instructions= field.
- Grok, Fireworks (default =:input=,
  =cl-llm-provider-api/src/provider.lisp:307=): prefix as leading developer
  messages, suffix as trailing developer messages.
- openai-compatible (own builder, =openai-compatible.lisp:585=): system
  message first, rendered context appended as the final system message.
- Anthropic (own builder, =anthropic/client.lisp:380=): system prompt, goal,
  hoisted developer texts, and rendered context all in the top-level
  =system= block.

* Findings

** 1. Codex puts per-turn volatile context inside =instructions= (critical)

=wire-protocol.lisp:224-227=: for =:top-level= placement the rendered
request-local context is appended to the =instructions= string. The built-in
contributors are volatile by design:

- =related-memories= (=src/agent/memory-context.lisp:50=) is keyed to the
  *latest user text* and renders match counts, =updated_at= timestamps, and
  excerpts. It changes on essentially every user turn, and mid-turn whenever
  the model writes a memory.
- =recent-user-operations= changes whenever the user runs a local form.
- =interpreter-discipline= and =self-improvement-review= fire mid-turn and
  periodically.

A changed =instructions= field invalidates the cached prompt from token
zero: the 12k-token tool block and the entire transcript re-tokenize at
uncached rates. On the ChatGPT route this is the default state of affairs -
in practice most user turns start with a full-prompt cache miss, which is
paid again on every tool round if a contribution mutates mid-turn.

The same builder already has the correct mechanism: the =:input= suffix
placement used by Grok and Fireworks, where the identical content arrives as
trailing developer messages and invalidates only itself. openai-compatible
independently does the right thing (=openai-compatible.lisp:601-605=).

Fix: on Codex, keep only the system prompt in top-level =instructions= and
deliver goal context plus rendered context as trailing =developer= input
items, exactly as the =:input= placement already does. This is a
placement-only change; content is identical.

Implementation update: Codex now keeps the system prompt in top-level
=instructions= and goal/context-tail as developer input items, alongside
separately projected anchored contributions. Identical currently supplied goal
and tail are anchored at their first tool-round boundary, so =U+A+C=,
=U+A+C+T1=, =U+A+C+T1+T2= extend the complete preceding input rather than
repeatedly moving =C= to the tail (=A= is opted-in anchored context). The exact
suffix guard uses only the actual goal and remaining tail from that assembly,
not the full rendering that includes =A=. Context changes, omission or partial
omission, user/developer/system boundaries, rewritten or shortened history,
and compaction reset placement. Placement evidence contains positions and
digests only; no previous prompt is replayed and durable history is unchanged.
This addresses request-prefix stability, not a guarantee of backend cache hits.
The assembly descriptions and measurements above describe the historical
review revision, not the current Codex wire layout.

** 2. The Anthropic client never sets =cache_control= (critical on that route)

There is no =cache_control= anywhere under =src/=. Anthropic prompt caching
is opt-in per block; without breakpoints, nothing is ever cached and every
request pays the full 23k-token prefix plus the whole transcript at list
price. This is the single largest per-dollar defect on the API-key route: a
long conversation costs roughly 10x what it should.

Fix, after finding 3 makes the boundaries stable: breakpoints in the
documented hierarchy - one on the tool array, one at the end of the stable
system prefix, one trailing the message history. Two interactions to handle:
=anthropic--input-messages= (=anthropic/client.lisp:242=) hoists
developer/system texts from the transcript into the top-level =system=
block, so a mid-conversation developer item would rewrite the system block
and defeat the breakpoint; and the volatile rendered context currently lives
in that same block and must move behind the history breakpoint (as a final
user-role block) first.

** 3. The system prompt embeds mutable session state at token zero (all providers)

=system-prompt--config= (=src/agent/prompt.lisp:152=) renders per request
(workspace AGENTS.md is also embedded and re-read each request; that is
intended behavior and out of scope here):

- *Agenda items* (=agenda-prompt-item-lines=, =src/state/agendas.lisp:362=):
  status, identifier, text, and memory ids per item. The model mutates the
  agenda through its own tools, so an =agenda.add= or a completion flips the
  system prompt mid-conversation and busts the entire prefix - self-inflicted,
  and invisible in any per-request diff because each request looks "correct".
- *Lisp image entries* (bounded at 12,000 chars): change whenever a worker
  image is saved or invalidated, again usually by the model itself.
- *Hurry-up* toggling rewrites the prompt for one request and back: two full
  busts per use. Same for the =(ste)= preference toggle.
- *Current date*: one bust per midnight, fine.

Fix: make the system prompt a function of configuration only - persona,
capabilities, workspace instructions, date. Move agenda and image state into
the request-local context suffix (they are exactly "ephemeral context
prepared for this request", and the suffix is already correctly placed on
every provider once finding 1 lands), or drop them to resource reads the
model performs when it cares. This ordering matters: fixing 1 and 2 without
3 buys little, because agenda flips would keep rewriting the top of the
prompt anyway.

Implemented after this measurement: request-local agenda rendering now includes
only =todo=, =doing=, =blocked=, and =note= items. Completed history remains
available through =resource.read agenda:current= without paying to inject it on
every provider request. The existing complete-line character bound still limits
unusually large active agendas.
On the same Autolith workspace, this reduced the live =session-state= contribution
from 48,291 to 3,153 instruction characters, or about 12,079 to 795 tokens in
=context-status=.

** 4. The tool bill: 46 tools, ~12.2k tokens, with cheap trims available

Measured composition (wire form, encoded names):

| namespace | tools | chars  | notes                              |
|-----------+-------+--------+------------------------------------|
| web       |     1 | 12,125 | one tool = 25% of the entire bill  |
| resource  |     2 |  8,489 | edit carries 14 operation variants |
| lisp      |    13 |  6,372 |                                    |
| rlm       |     3 |  6,151 |                                    |
| self      |    12 |  5,771 |                                    |
| task+job  |     5 |  3,547 |                                    |
| others    |    10 |  6,469 |                                    |

- =web.run= alone is ~3k tokens and ships on every provider except Grok,
  which filters it (=grok/client.lisp:98=) because backend search replaces
  it. Codex requests with hosted web search enabled carry *both* the hosted
  tool and the unused local schema; a configuration with web search disabled
  still pays for it while the system prompt tells the model it is absent
  (=system-prompt--web-run-p=). Gate registration on
  =configuration-web-search-mode= and filter it wherever a hosted tool is
  served, mirroring Grok.
- =lisp= plus =self= are 25 of the 46 tools. They are Autolith's identity,
  but several (=self.rollback=, =self.discard=, =agenda.transport=,
  =lisp.discard-image= class of operations) are rare-path administration.
  Worth an audit pass for description length rather than removal: the
  schemas are the cost, not the capability. Codex ships five tools by
  keeping the how-to in the prompt; the middle ground is shorter
  descriptions on rare tools, not fewer tools.
- Trimming matters most for cache *writes* and misses: with stable prefixes
  the 12k tokens cost full price once per conversation - and once per task
  child, since every child conversation carries its own copy of the prefix,
  so fan-outs multiply whatever the prefix costs.

Implemented after this measurement: capable GPT-5.4+ Codex subscription models
now receive native namespace entries whose functions use =defer_loading=true=,
plus hosted =tool_search=. Unsupported routes retain the byte-for-byte eager
fallback. In the protocol fixture, model-visible tool metadata falls from 169
to 122 JSON characters (28%); the full registry keeps only namespace names and
descriptions visible initially instead of the measured 48,924 schema
characters. Reviewed references: OpenAI's
=https://developers.openai.com/api/docs/guides/tools-tool-search=; Codex
=https://github.com/openai/codex= at =ba6cf9c69277caec51a4c12c5b7401a9920930e0=,
notably =codex-rs/core/src/tools/handlers/tool_search.rs=,
=codex-rs/core/src/tools/context.rs=, and
=codex-rs/core/tests/suite/search_tool.rs=; pi
=https://github.com/badlogic/pi-mono= at
=8fa7eebd235355522c8104166b4f1f959b4e2f10=, notably
=packages/ai/src/api/openai-responses-shared.ts= and
=packages/ai/test/deferred-tools.test.ts=. OpenCode
=https://github.com/anomalyco/opencode= at
=ac1c048e6420eb4c728fd3e343a1ba7b076cba92= was reviewed; its code-mode
catalog is a textual fallback and was intentionally not adopted.

** 5. Base64 wire names cost more than they need to (small, everywhere)

=provider-wire-function-name--encode= (=wire-protocol.lisp:22=) renders
=workspace.read= as =a= plus base64url of =namespace NUL name=: 786 chars of
encoded names versus 542 dotted across the registry, and base64 tokenizes
worse than words (roughly one token per 2-3 chars versus 4). The name is
repeated in every tool definition, every historical function call item, and
every name the model *generates* (output tokens, the expensive kind). A
=namespace__name= encoding fits the same =^[a-zA-Z0-9_-]+$= grammar,
reverses trivially, reads naturally in traces, and would also have sidestepped
the DeepSeek bare-name echo failures that needed the fallback decoder.
Migration note: the change must be simultaneous with conversation replay
normalization, since historical items store namespaced calls and re-encode
on the way out.

** 6. Cache-key and toggle hygiene (small)

- openai-compatible sends no =prompt_cache_key=; Codex, Grok, and Fireworks
  do. OpenAI-compatible backends that support it route cache lookups better
  with one. One field.
- Goal context rides in the instruction *prefix* on every Responses
  provider, ahead of all history, so setting or clearing a goal
  mid-conversation is a full bust. Task children make this expensive: every
  child carries its own goal (=src/task/child.lisp:613=) ahead of the
  inherited parent transcript, which is what blocks fan-out prefix sharing
  (see Further measures). It is request-local guidance; it belongs with the
  rendered context in the suffix.
- Restricted tool rounds flip the tool array between the full set and =#()=
  (=agent/runtime.lisp=, =tool-schemas-p=); each flip is a prefix change.
  Only relevant inside restricted frames, which are short - acceptable, but
  worth knowing before reusing the mechanism on primary conversations.
- MCP dirty refresh re-registers a server's tools each agent loop iteration
  when dirty (=agent/runtime.lisp:948=). =tool-registry-provider-schemas=
  preserves insertion order through an ordered map, so confirm a
  re-registered server lands in its original position rather than at the
  end; a reorder is a silent full bust.

** 7. What is already right

Worth listing so nobody "fixes" it:

- Tool results are bounded to 8,000 chars before entering history
  (=registry.lisp:440=), so transcript growth is controlled.
- The advisory context budget is ~1,500 tokens with hard evidence caps -
  the suffix is small; its *placement*, not its size, was the problem.
- =prompt_cache_key= is the conversation identifier on the routes that send
  it, and task children reuse the root key as a routing hint
  (=src/task/child.lisp:565=).
- Restricted roles and frames already shrink the schema set to the
  allowlist (=agent/runtime.lisp:1106=, =:canonical-names=), not just
  execution - the filtering machinery for finding 4 exists.
- =text.verbosity low=, =store false=, bounded SSE lines and events,
  per-family reasoning privacy, and the 80% compaction threshold are all
  reasonable. Encrypted reasoning replay is required for quality and is
  cheap once the prefix caches; it is expensive today only because of
  findings 1-3.
- openai-compatible already appends the volatile context after history.

* Further measures

** 8. Cache telemetry first: Autolith cannot see its own hit rate

No reference to =cached_tokens=, =prompt_cache_hit_tokens=, or
=cache_read_input_tokens= exists under =src/=, so none of the effects in
this report are observable from inside Autolith today. Providers report the
split on every response: OpenAI-family under
=usage.prompt_tokens_details.cached_tokens=, DeepSeek as
=prompt_cache_hit_tokens=, Anthropic as =cache_read_input_tokens= and
=cache_creation_input_tokens= once breakpoints exist. Record the cached
share into the per-request usage records the conversation already persists,
and surface a per-conversation hit rate (in =(usage)= or the status line).
Every other change in this report then has a number instead of a vibe, and
a regression - a reordered tool, a new volatile prompt field - shows up as
a hit-rate cliff instead of a mystery on the invoice.

** 9. Fan-out prefix sharing is one move away

The task system was clearly built for it: every child conversation reuses
the *root* conversation's =prompt_cache_key= (=src/task/child.lisp:565=)
and begins with the inherited parent transcript. What defeats it is
ordering: each child's goal context (role plus assignment,
=src/task/child.lisp:613=) rides in the instruction prefix *before* that
shared history, and on Codex the per-child rendered context lands in
=instructions= too (finding 1), so the N children of one fan-out present N
distinct prefixes and share nothing.

Move goal context and rendered context behind the inherited history
(findings 1 and 6) and every same-role child of a fan-out shares one
cached prefix: system prompt, tools, and the entire parent transcript are
paid once per fan-out instead of once per child. For =rlm-map= and
=task.run= batches over a large parent conversation this is the largest
single saving in this report. Children whose role allowlists differ send
different tool arrays and therefore share only within a role - still a win,
worth keeping role tool sets identical when it does not cost capability.

** 10. Compaction is the free moment to slim the transcript

Compaction already rewrites the conversation, so the cache reset is paid;
anything else dropped in the same pass is free. Candidates the current
compaction should be audited for: prior-turn encrypted reasoning items
(large base64 blobs that no longer influence sampling), superseded
=resource.read= outputs (an old read of a URI that a later read replaced -
stale content is worse than absent), and aged image inputs. Outside
compaction none of these are worth touching: deleting an item mid-flight
rewrites the prefix and costs a full miss.

** 11. Tools are documented twice

The system prompt template (685 lines) teaches the lisp, self, task, and
RLM surfaces at length, and the same tools carry long schema descriptions -
both go up on every request. Codex keeps schemas terse and teaches in the
prompt; either home works, paying for both does not. A related mechanical
trim: the REPL-control parameter block repeats across all 13 =lisp.*=
schemas. A description audit that assigns each tool one documentation home
should recover a few thousand tokens of the fixed prefix with no capability
change.

** 12. Consciously rejected: server-side conversation state

=store true= plus =previous_response_id= on the Codex route would eliminate
history replay entirely. Rejected for the same reasons codex itself ships
stateless: it surrenders branching, steering-time editing, and the privacy
stance, and it makes the transcript's ground truth live on the provider.
Stateless plus a stable cached prefix achieves most of the saving without
those costs; this report's fixes are that path.

* Suggested order of work

0. Finding 8: cached-token telemetry, so every step below is measured
   before/after on real conversations.
1. Finding 3: freeze the system prompt; move agenda and image state into the
   request-local suffix. This is the enabling change.
2. Finding 1: Codex placement - system prompt stays top-level, everything
   volatile becomes trailing developer input. With 1+3, the ChatGPT route
   should hit cache on every request after the first of each turn, and
   usually across turns.
3. Finding 6's goal-context move rides along with 2 for free.
4. Finding 2: Anthropic =cache_control= breakpoints, now that boundaries are
   stable. Largest per-dollar win on API-key routes.
5. Finding 4: gate =web.run=, audit rare-tool description length.
6. Finding 5: =namespace__name= wire encoding, coordinated with replay.

Findings 9 and 10 fall out of the same work: 9 is unlocked by steps 1-3
(verify with a two-child fan-out showing one cache write and N-1 reads),
and 10 rides the next compaction change.

A useful acceptance test for 1-4: two consecutive requests in the same turn,
and two consecutive turns with an agenda mutation between them, must produce
byte-identical request prefixes up to the trailing context block. That
property is checkable in the existing provider request tests without any
provider round trip.

* Method

Measured in a live image at =ba5ac68= with the real Autolith workspace: full
default registry plus task tools (MCP excluded, so user configurations sit
above these numbers), Codex wire encoding, =json-encode= lengths, tokens
approximated as chars/4 (JSON and base64 tokenize denser, so tool figures
are, if anything, underestimates). Cache pricing referenced as the
documented ~0.1x cached-read multiplier on OpenAI and Anthropic; on
subscription routes the same misses surface as rate-limit burn instead of
dollars. Not audited: per-MCP-server contributions, image inputs, and the
localgroup/handoff paths.
