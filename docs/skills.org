* Skills

A Skill is a named bundle of instructions for the model,
if you have used clankers for any significant measure of time.

Autolith shows the model a small catalog first.

The model can call =skill.load= to load the entire skill contents.

They are request-local.

Put this in =.autolith/skills/release-check/SKILL.sexp=:

#+BEGIN_SRC lisp
(:autolith-skill
 :version      1
 :name         "release-check"
 :description  "Verify a release from source through its packaged artifact."
 :instructions
 "Follow the repository release procedure completely.
Run every relevant check before reporting success.")
#+END_SRC

Then ask for release verification. If the catalog describes a matching
Skill, the model selects it with =skill.load= before work that depends
on those instructions.

Ask your clankers to convert existing skills into the Autolith format.

There is a good reason why we do this, and in the future, Autolith will
be able to convert your skills automatically.

* Writing skill

A Skill directory contains one file named exactly =SKILL.sexp=. It is
one bounded top-level form with these required fields:

- =:autolith-skill=
- =:version=
- =:name=
- =:description=
- =:instructions=

=:instructions= is the instruction body. You can of course refer
to neigboring files there.

Autolith rejects unsupported versions, unknown or duplicate fields,
malformed data, extra forms, reader labels, circular or shared
structure, and values of the wrong type, and so on and so forth.
You will get an error, you will know what's wrong.

* Locations

Scans these roots, first match wins:

1. =.autolith/skills/= at the project root
2. =${XDG_CONFIG_HOME:-~/.config}/autolith/skills/=
3. bundled Skill roots

Outside Git, the workspace directory is the project root. Scans are
recursive. Only the case-sensitive filename =SKILL.sexp= counts.

Each consecutive location overrides the previous ones, so
you can have a project local version of a skill if you like.

* Loading

- Every inference provider request gets a bounded catalog when Skills exist
- The catalog has names, descriptions, and paths
- =skill.load= records the selected name and filesystem identity for the
  current logical turn
- It returns a short confirmation that the model did not fuck up skill selection
- The terminal finalizes a visible =◆ loaded skill: NAME= transcript marker
  when selection succeeds; the marker survives ordinary redraws but is not
  written to durable conversation history
- At the next provider boundary, Autolith will reread the file and
  injects the current version of =:instructions= as request-local context
- Selected Skills stack in catalog order
- Child agents may load Skills only when their role permits =skill.load=.

* Diagnostics

The =(skills)= commands inspects the catalog. It shows
selected definitions, descriptions, paths, and diagnostics for rejected
or shadowed files. With no Skills, it shows the roots where you can
create one.

You can also use =(context)= to show the catalog, selected contributions,
omissions, and contributor failures.
